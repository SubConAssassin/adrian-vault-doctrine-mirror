### 🔴 THE ITEM v1 MISSED — Claude Code auto mode becomes the default on 14 August

**Why v1 missed it, and it is a reusable method lesson:** v1 read the Claude Code *changelog* (v2.1.223–226) and Anthropic's *newsroom*, and correctly reported that the newsroom has exactly one August post. **The auto-mode default was announced on the product blog, the docs and Threads — none of which are on the usual check-list.** A harvester that checks `anthropic.com/news` plus the changelog misses the single most operationally significant Anthropic change of the month.

- **Announced 7 August; effective 14 August 2026.** New sessions on **Pro, Max and Team** run in **auto mode**: rather than prompting per action, Claude Code **routes each tool call through a classifier** targeted at blocking anything *"irreversible, destructive, or aimed outside your environment."* [CONFIRMED first-party — [Anthropic blog](https://claude.com/blog/auto-mode-default-in-claude-code), [auto-mode config docs](https://code.claude.com/docs/en/auto-mode-config)]
- **Still opt-in on Claude Enterprise and the Anthropic API**, with Anthropic stating it plans to default there "in the coming month." [CONFIRMED first-party]
- **Opting out is trivial and a self-set default is respected:** `Shift+Tab` in the CLI or the desktop mode dropdown; an existing self-set default triggers a **one-time switch prompt**; **an org-managed default is left unchanged.** Managed settings expose `defaultMode` and `disableAutoMode`. [CONFIRMED first-party]
- **Meter note:** Anthropic states it is **"no longer charging Claude Code users on Pro, Max and Team plans for that classifier overhead, effective today"** (7 Aug). [CONFIRMED first-party]
- **The precedence order, which determines which vault rules become enforceable and which stay advisory:**
  1. `permissions.deny` — **blocks before the classifier is consulted; neither the classifier nor user intent can override it.**
  2. `permissions.ask` — content-scoped ask rules evaluate before the classifier and **always** prompt, even in auto mode.
  3. Inside the classifier: `hard_deny` (unconditional) → `soft_deny` (destructive, clearable by explicit intent) → `allow` (exceptions to soft blocks) → explicit user intent. *"General requests don't count as explicit intent"* — "clean up the repo" does not authorise a force push; "force-push this branch" does.
  4. A boundary stated **only in conversation can be lost to context compaction** — the docs say so outright and recommend an ask/deny rule "for a durable guarantee."
  [CONFIRMED first-party — [auto-mode config](https://code.claude.com/docs/en/auto-mode-config)]
- **🔴 Two configuration facts with direct vault consequences.**
  - **The classifier reads the same `CLAUDE.md` content Claude itself loads**, so a project instruction like "never force push" steers the classifier as well as the model. **Our instruction layer is now partly a security configuration.**
  - **The classifier does NOT read `autoMode` from `.claude/settings.json` or `.claude/settings.local.json`** — deliberately, because *"a checked-in repo or a build step could otherwise inject its own allow rules."* Trust config must live in `~/.claude/settings.json` or managed settings. Behaviour changed at **v2.1.207**; any existing `autoMode` block in `settings.local.json` needs moving.
  [CONFIRMED first-party]
- **🔴 The default that conflicts with our own doctrine: auto mode allows pushes to any branch of the working repo *including the default branch*, plus PR creation, by default.** Changed at **v2.1.211** — previously pushes were allowed only to the working branch, agent-created branches, and "routine pushes to the default branch." Deploy-marked branches (`production`, `release`, `gh-pages`) are still judged on their own terms, and force pushes / secrets-in-commit stay blocked. **This vault's working branch is `main`.** [CONFIRMED first-party]
- **The safety numbers, with the honest counterweight.** Anthropic reports auto mode caught a planted dangerous command **89%** of the time vs **13.6%** for human reviewers, and cites an independent **Trajectory Labs** audit — **72 attack scenarios × 10 runs = 720 attempts** against Fable 5, Opus 5 and Sonnet 5, none of which landed. Anthropic itself says auto mode **"does not eliminate risk,"** and reports **Apollo Research's red team got past it ~7% of the time on a hardened adversarial set**. [Vendor figures CONFIRMED as reported; independent replication UNVERIFIED — [explainx](https://explainx.ai/blog/claude-code-auto-mode-default-pro-max-team-august-2026), [The New Stack](https://thenewstack.io/claude-code-auto-mode/)]
- **Simon Willison's objection is the one to carry, because it is architectural rather than statistical:** 89% *"still leaves 11% of cases where auto mode would not have prevented the action,"* and he doubts any classifier stops the realistic attack where **the fetch command itself is the exfiltration**. His prescription — **architecturally limit what the agent can reach** rather than trusting the safety layer — is the same conclusion §11.1a reached independently after the unauthorised-spend incident. [CONFIRMED — [simonwillison.net](https://simonwillison.net/2026/Aug/8/auto-mode/)]
- ⚠️ **One secondary figure deliberately NOT carried.** A TechCrunch summary attributes the testing to "1,053 paid users." No other source repeats it, and it is numerically identical to an unrelated number in our own vault history — exactly the coincidence that gets a wrong number laundered into canonical. **Recorded UNVERIFIED, not used.** [[TechCrunch](https://techcrunch.com/2026/08/09/anthropic-is-turning-claude-codes-auto-mode-on-by-default/)]

### 🔴 Imagen 4 shuts down 17 August — and here v2 corrects v1

- **First-party, verbatim: *"The Imagen 4 standard, ultra, and fast endpoints are deprecated and will be shut down on August 17, 2026."*** Affected IDs: `imagen-4.0-generate-001`, `imagen-4.0-fast-generate-001`, `imagen-4.0-ultra-generate-001`. Named replacement: **Gemini 3.1 Flash Image**. **Not a drop-in** — `generate_images()` is gone; generation moves to `generate_content()`, so a stale caller **fails hard rather than degrading**. [CONFIRMED first-party — [Imagen docs](https://ai.google.dev/gemini-api/docs/models/imagen)]
- **🔴 v1 recorded this as CLEARED on the evidence `grep -ril imagen tools/` → no matches. That evidence is wrong.** A direct filesystem walk this session found **three** matching files: **`tools/gemini-image.py`, `tools/lanes.py`, `tools/metered_guard.py`.** The likely cause is benign and known: **a plain recursive `grep` over `tools/` does not complete on this box right now** — the same command was launched twice in this session and was still running after 120s and after 90s under the current disk-pressure/file-provider conditions, returning empty output. **An interrupted grep and a clean grep look identical.** This is the same failure class as the vault's existing `timeout`-is-not-installed and `shuf`-does-not-exist lessons: **a tool that silently degrades produces a confident false negative.**
- **The conclusion survives, for a different reason — verified by reading the file.** `tools/gemini-image.py` calls `client.models.generate_content()` with the fallback chain `gemini-2.5-flash-image` → `gemini-2.5-flash-image-preview` → `gemini-2.0-flash-preview-image-generation`. **It does not touch the `imagen-4.0-*` endpoints, so it does not break on 17 August.** [VERIFIED by direct file read, 10 Aug]
- **Two real defects the correct check surfaced, which the false-negative check could not have:**
  - **`tools/lanes.py:80` labels the script `"tools/gemini-image.py (Imagen)"`** — a misnomer in the machine-readable lane registry. A future session would reasonably conclude we sit on a surface that dies on 17 August, or dismiss a genuine Imagen dependency as already-checked.
  - **The model pins are a full generation stale.** Google's named current model is **`gemini-3.1-flash-image`**, present in today's live model list; our chain tops out at `gemini-2.5-flash-image`. Same defect class as §14.7's `agy` repin: **a pin that still resolves is not a pin that is current.**

## B. INNOVATIVE USES — what people are actually doing

**This week's community signal is about restraint and permissions, not capability** — bounding agents so they stop, and deciding what they may reach.

- **The week's dominant practitioner conversation is about agent *permissions*, not agent *capability*.** Auto mode reframed the debate from "can it do the task" to "what is it allowed to reach," and **Willison's architectural prescription — limit access rather than trusting the safety layer — is the reusable takeaway.** [CONFIRMED — [simonwillison.net](https://simonwillison.net/2026/Aug/8/auto-mode/)]
- **🔴 The MCP-versus-CLI overhead argument has hardened into numbers, and it is load-bearing for this vault.** Community reporting puts **MCP operations at 32,000–82,000 tokens of context overhead versus roughly 200 for an equivalent direct CLI call.** The settled position is not "MCP is dead" but that there are two failure modes: **a skill nobody reliably triggers, and an MCP server that blows the context budget.** MCP's defensible advantage is **isolating the auth flow outside the agent's context window**. [Figures secondary/INFERRED — [HackerNoon](https://hackernoon.com/mcp-is-dead-the-cli-is-winning-the-ai-agent-stack), [Atlan](https://atlan.com/know/ai-agent/ai-agent-skills/agent-skills-vs-mcp/), [Developers Digest](https://www.developersdigest.tech/blog/what-hacker-news-gets-right-about-ai-coding-agents-2026)]
- **`maxTurns` is now named as mandatory practice for bounded subagents, not an optimisation.** Stated failure mode: subagents "get expensive when they keep exploring, testing, and re-checking without a clear stopping point." [CONFIRMED as community guidance — [UX Planet](https://uxplanet.org/best-practices-for-claude-code-subagents-optimization-7ff0dd3e20b5), [sub-agents docs](https://code.claude.com/docs/en/sub-agents)] **⚠️ INFERRED as best practice, not vendor-measured.**
- **The parallelism sweet spot is given as 3–5 concurrent subagents, with "beyond 10 rarely provides additional benefit and increases costs significantly."** **Worth holding against our own numbers:** §11.3 caps CLI clients at 10–12 on the M1 Max, §5 allows 16× subagent fan-out. Different things (CLI processes vs Claude subagents), and the community number is a *value* claim (diminishing returns), not a *capacity* claim.
- **The named test for whether a subagent should exist:** repeated often · describable as a separate role · likely to produce context noise · better with restricted tools · better on a cheaper/faster model · useful across projects. *"The biggest mistake is treating subagents like a collection of tools for every possible activity."* This is §1b.3's tier-pinning law arrived at independently.
